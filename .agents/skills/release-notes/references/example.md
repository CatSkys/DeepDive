# 同一批改动的两种写法

取自本仓真实数据。上面是**提交主题**（工程语气，`git log` 直接给的那种），下面是同一批改动
经过挑选与改写后的**更新说明**。

## 提交主题（不这么写）

```
- fix(截图/提取文字): 识别钉到 Vision rev2——几十秒的真因是默认那版大模型
- feat(迷你面板): 进行中动效两种形态并存，命令中心的设置里可选
- fix(迷你面板): 命令中心只留一个「置顶」，并修好它——卡片页的桥白名单把 set-pref 丢了
- fix(打包/交付): 打包前停旧实例；版本号递增改成失败即还原
- merge: 提取文字冷启动挪出用户的路（feat/shot-ocr-perf）
```

问题一眼可见：`Vision rev2`、`set-pref`、`桥白名单`、`prune`、`§5.5`、版本号还原——这些是
写给维护者的，用户既不知道也不关心。「几十秒的真因」是对我们真因，对用户只是"以前要等很久"。

## 更新说明（这么写）

```markdown
## 本版变更

- 截图取字快了很多：以前首张要等几十秒，现在几乎没有等待
- 迷你面板的「进行中」动效给了两种样式，可在设置 → 命令中心里选
- 修好了「置顶」：命令中心只留一个，且点了真的生效
```

对照着看这三条是怎么出来的：

| 提交主题 | 处理 |
|---|---|
| `识别钉到 Vision rev2——几十秒的真因是…` | 留结果（更快），丢实现（换了哪个识别器） |
| `进行中动效两种形态并存，设置里可选` | 基本直译：这条本来就是用户可见的 |
| `命令中心只留一个「置顶」，并修好它——桥白名单把 set-pref 丢了` | 留前半句用户视角（只留一个、真的生效），后半句是实现细节，删 |
| `打包前停旧实例；版本号递增改成失败即还原` | **整条不进说明**：发布链的事，用户感知不到 |
| `merge: 提取文字冷启动挪出用户的路` | 合并提交不进说明（发布链已按 `--no-merges` 排除） |

## 反面例子

```markdown
## 本版变更

- fix(截图): 撤掉那条 3s 死线，识别器改在标注时后台预热（PITFALLS §5.5）
- refactor: publish-release.sh 的 ${VAR} 加花括号，修掉 bash 3.2 吞全角字符的坑
- 内部：prune-dsh-runtime 清单同步到 engine 0.1.5-rc.1
```

三条都不该出现：第一条是提交信息原文，第二条是发布链内部的事，第三条用户连它是什么都不知道。
