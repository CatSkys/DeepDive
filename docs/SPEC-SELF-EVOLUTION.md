# SELF-EVOLUTION — 自进化（经验沉淀与校验闭环）spec（草稿 · 待拍板）

> **状态（2026-09-12）：草稿，未动工**。范围与口径待用户确认（§9 开放问题）。本文件是「自进化」这件事的**唯一事实源**：进化什么、怎么变异、谁来选择、效果怎么算。
> 相关：协议块与建议卡沿用 `docs/SPEC-AUTOMATION.md §3` 的通道；校验复用同文件的定时任务；引擎侧能力事实归 `docs/DSH-WIRE.md`；壳桥消息清单归 `frontend/src/host.ts` 头部。

## 0. 一句话

把一次会话里**挣到的工程经验**（试错才走通的路径、非显然的项目事实、踩过的坑）就地沉淀回仓库的**知识家**，并且每条都带**可证伪的效果主张**：到期用会话日志自动校验，无效就退役、并把教训回流去收紧提议策略。进化的对象是**规则 / 技能 / 文档这一层**，不碰产品代码。

## 1. 为什么是「知识层自进化」（三条约束）

- **没有裁判**。AHE 能十轮把 Terminal-Bench 从 69.7% 抬到 77.0%，是因为它有可复现评估集能自动判死活；我们的裁判是交付链和你本人。所以闭环只能停在"提出带证据的结论 → 人点头 → 到期用日志校验"，任何"能力提升 X%"的说法在没有独立数据时都不许出现（§6 反作弊条款）。
- **仓库怎么被消费**。这个仓库靠提交信息、文档、截图消费，知识本来就分家住在 `AGENTS.md`（规则）、`docs/PITFALLS.md`（真实事故 + 处置 + 诊断锚点）、`docs/SPEC-*.md`（语义边界）、引擎技能正文里。所以进化的动作天然是**往已有的家里补一条**，不是另起一个平行的学习库。
- **persona 页的教训**。设置里的「自定义指令」被你否过一次——空文本框既不知道该写什么也没有上下文。值钱的是**循环**：什么时候值得记、拿什么证据、记到哪个家、怎么证明它真的省了事。

## 2. 自进化四要素（本设计怎么落到这四个词上）

| 要素 | 在本设计里是什么 |
|---|---|
| **变异** | 一条提案 = 对某个知识家的**有界编辑**：文本由模型写，落点由协议锚定（`home` + `anchor`），改动范围限于允许清单（§5）。 |
| **选择** | 双门：①**人审**（建议卡确认才落库）；②**到期校验**（窗口内事故签名复现次数 / 同类流程的工具调用步数），未过即判无效。 |
| **存档** | 仓库 git：每次落地 = 一次带因果说明的提交；**谱系** = 提交历史 + 文档里的 `lesson` 标记行（含被否决与已退役）。 |
| **二级进化** | **提议策略本身**（`docs/EVOLUTION-POLICY.md`，动工时创建：什么算值得提、怎么措辞、阈值多少、允许清单）按一级结果更新。这是本设计里唯一被"改"的 harness 层——它是提示/规则，不是代码。 |

**反退化**：被否决与已退役的条目留在谱系里。同一件事反复提，会被策略判为低价值信号 → 所以「复提率」是必须盯的指标（§6 指标 C）。

## 3. 形态：六段闭环

1. **触发**（不是每轮都提）。只在四种信号上出手：试错数轮才走通的路径；非显然的项目事实（凭据在哪、怎么验证线上、这条流水线的隐藏前置）；同一个坑第二次出现；用户明说"记住这个"。判据直接借 `Kulaxyz/self-learning-skills` 的"识别黄金路径时刻"，连**死路一起记**（"下次别再试 Y"往往比成功更有价值）。
2. **提议**。模型在回复里输出一个 info string 为 `lesson` 的围栏块（§4），字段强制：落点、证据、**可校验的预测**、边界声明。缺少可量预测的只能标 `style` 类（§6）。
3. **门**。消息流里出一条「沉淀建议」卡（与定时任务建议卡同族：卡头行 + 右端按钮 + 内容组），展示：落点、要插入的文本、证据（逐字）、预测与到期日。按钮 = 落库；也可以"只在编辑器里打开看看"，或者丢弃（丢弃同样记录在案）。
4. **落库**。应用按锚点把文本插进目标文件，然后提交一次 git（提交信息含因果与证据指针）。落库即写 `lesson` 标记行（§5.3）。**一键撤销** = 反向提交（或 `git revert`），标记行置 `retired`。
5. **校验**。窗口到期（默认 14 天，见 §9）由一条**内置定时任务**执行：它按台账生成指令，让 agent 用 shell 去挖会话日志（`zstd -dc <session>.jsonl.zstd | grep …`），报出签名复现次数或步数对比；结果写回标记行。**校验数据必须来自日志/git，不允许自评**。
6. **退役与回流**。判无效 → 标记行置 `retired`（文本保留，附失败原因）→ 同时产生一条**二级提案**：改 `EVOLUTION-POLICY.md` 里对应的判据或措辞规则。这样"无效"不是终点，而是策略的一次变异。

## 4. 协议：`lesson` 围栏块

````text
```lesson
{
  "home": "pitfalls",
  "anchor": "### 4.17 桥端口一变",
  "insert": "### 4.18 …（要写进去的完整 Markdown）",
  "evidence": [
    {"kind": "log", "quote": "Killed: 9 …", "source": "engine.log"},
    {"kind": "commit", "ref": "33d0ba1b", "note": "same symptom, 9-12"}
  ],
  "predict": {"metric": "repeat-incident", "signature": "Taskgated Invalid Signature", "windowDays": 14},
  "style": false
}
```
````

| 字段 | 说明 |
|---|---|
| `home` | 允许清单里的知识家（§5.1）。不在清单 → 整条拒绝。 |
| `anchor` | 落点的**标题锚**（某节标题的前缀）。找不到锚点 → 整条拒绝并回报，**不猜位置**。 |
| `insert` | 要插入的完整文本（模型按该家的写作规范写好，应用不改写）。 |
| `evidence` | ≥1 条，逐字可核（日志原文 / 文件:行 / 提交号）。**逐字**是硬要求。 |
| `predict.metric` | `repeat-incident`（签名复现次数，目标 0）或 `steps`（同类流程工具调用数，目标至少 −30%）。 |
| `predict.signature` | 可被 grep 的签名（错误串、命令片段、文件路径）。**必须是日志里真能命中的形态**——协议要求提议方在提出前先自证一次能 grep 到，否则降为 `style`。 |
| `style` | `true` = 风格/偏好类，不设校验、**不计入效果统计**。 |

与 `automation` 块同族：同一个 `protocol.ts`、同一张卡、同一条"提议 → 人确认"的语法，只是落点从"任务清单"换成"知识文件"。

## 5. 通道与落点

1. **允许清单**（写在 `EVOLUTION-POLICY.md`，动工时创建，可演进）：`docs/PITFALLS.md`、`AGENTS.md`、`docs/SPEC-*.md` 的设计段、`docs/EVOLUTION-POLICY.md` 自身、以及（开放问题 §9.4）任务模板。**产品代码、脚本、配置一律不在清单内**——这是 penguin-harness 的 `CONTRACT.md` 那条纪律的直译。
2. **读**：应用经 `/api/file?path=…`（预览同款受控面）读知识文件，解析标记行。
3. **写**：新增一条壳桥消息（写文件 + `git add/commit`），沿用 `SessionAdmin` 的原子写模式（临时文件 + `replaceItemAt`），失败明确回包不静默。**为什么由壳写而不是让 agent 写**：确定性、会话关掉也生效、可原子回滚；文本本身仍是模型写的（`insert` 原样落盘）。反方案见 §9.1。
4. **台账与知识同家**：状态写在文档里的标记行，不另建库——
   `<!-- lesson: id=l-7f3a home=pitfalls metric=repeat-incident sig="Taskgated Invalid Signature" window=14d landed=2026-09-12 due=2026-09-26 status=pending -->`
   校验后同一行补 `verified=… recurrences=0`，退役则 `status=retired`。**理由**：这条知识与它的验收状态必须在同一个 git 提交里，人才可能在 review 时看明白；另开一份 `.json` 会立刻漂移。（备选见 §9.2。）

## 6. 效果口径（"明确有效果"就按这三条算）

**指标 A · 重复事故率（主张级别的硬指标）**：每条 `repeat-incident` 经验在窗口内被 grep 到的次数。目标 **0**；≥1 即判无效。数据源是会话日志（`<DSH_HOME>/sessions/<bucket>/<sessionId>/session.v3.jsonl.zstd`，agent 用 `zstd`+`grep` 挖，应用不自己解压）。

**指标 B · 关键流程步数（过程级别的硬指标）**：`steps` 类经验落地前后，同一流程（按签名匹配）在会话里的工具调用数均值。目标至少 **−30%**。同样来自日志。

**指标 C · 循环自身的健康度**：采纳率（采纳 / 提出，目标 ≥50%）与**复提率**（同一签名被重复提议的比例，目标趋近 0）。完全从标记行算出。

**基线不用等**：A 与 B 都能**回溯计算**——落地前先在现有日志里跑一遍就得到"之前是多少"。所以第一批经验落地后**几天内**就能给出"前后对比"，而不是等一个月才敢说效果。

**展示**：设置 → 自动化分区里加一块「经验台账」：每条一行（落点 / 预测 / 到期日 / 状态 待校验·有效·无效·已退役 / 复现次数），顶部三行汇总（累计落地 N，有效 M，退役 K，重复事故率 A→B）。卡片上也要写明到期日——落库那一刻用户就知道"这条什么时候会被验"。

**反作弊条款**：① 校验结果只能来自日志或 git，不许模型自评；② 没有 `predict` 的条目一律 `style` 类，**不进任何统计**，防止用"感觉更好用"凑数；③ 签名必须自证可 grep（§4），避免造一个永远命中 0 次、看着"有效"的假签名；④ 窗口内样本不足（该流程没再出现过）一律标 `未验证`，不折算成成功。

## 7. 非目标

- 不改产品代码、不改脚本与配置——本设计里没有任何"让 agent 改代码"的路径。
- 不自动合并：任何落库都必须过人这一关。
- 不建平行的知识库/记忆库；台账与知识同家（§5.4）。
- 不做隐藏的全局指令块（那是 persona 页的老路）。
- 不宣称没有独立数据支撑的提升。

## 9. 开放问题（待你拍板）

1. **落库执行者**：壳直接写盘 + 提交（确定性、会话关了也生效、可原子回滚）／让 agent 在会话里写（更贴各家的写作规范，但要会话活着，且要再花一轮 token）。我倾向前者（文本已由模型写好，落盘是机械动作）。
2. **台账位置**：文档内标记行（与知识同家、随提交一起 review）／单独 `.deepdive/lessons.json`（不污染文档，但会漂移）。我倾向前者。
3. **默认窗口与频率**：14 天窗口、每天跑一次校验？还是按经验类型给不同窗口（事故类 7 天、流程类 30 天）？
4. **允许清单**是否纳入任务模板（`docs/SPEC-AUTOMATION §2` 那四张卡）与 `docs/WORKING-AGREEMENTS.md`？
5. **校验任务**由应用在第一条经验落地时自动创建，还是要求用户手动开？

## 10. 验收口径（动工后按这个验）

- 会话里说一句"记住这个"，能出「沉淀建议」卡；点落库后目标文件多出该节、多出标记行，且有一次 git 提交（`git log` 可查）。
- 故意点"丢弃"，标记行以 `rejected` 留档，且重复提议同一签名的第二次会被策略压低优先级（复提率可观测）。
- 到期后校验任务跑一次，标记行补上 `verified` 与 `recurrences`；人为把某条经验的签名重新制造一次，校验必须判它**无效**并产生二级提案。
- 台账里的"前后对比"能在现有日志上算出来（基线不依赖新数据积累）。
