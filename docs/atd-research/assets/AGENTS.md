# Repository Guidelines

These rules define project constraints and completion criteria. The [OpenAI prompting guidance](https://developers.openai.com/api/docs/guides/latest-model#prompting-best-practices) informs execution, instruction clarity, communication, delegation, and verification; the access limits and product decisions below are project policy.

## Instruction Priority And Applicability

- Follow system and developer instructions first. Explicit user instructions in the current conversation override repository and skill guidelines for the scope they address. Read applicable nested `AGENTS.md` files before editing their subtrees.
- Apply domain-specific requirements to work that touches that concern. Command references and examples describe available tools, not a checklist for every task. General implementation authorization does not override the explicit documentation, history, runtime, delegation, or protected-content limits below.
- Before treating a skill as an approval gate, check its exact requirement against the current scope and existing authorization. If it causes a pause, confirmation request, incomplete work, or departure from the user's intent, link to the exact `SKILL.md`, quote the relevant instruction, and distinguish the requirement from your interpretation.
- When updating these guidelines, consolidate a rule in its owning section. Keep hard requirements for project invariants; express judgment calls through conditions and observable outcomes. Avoid duplicate instructions, speculative restrictions, and volatile implementation details that belong in source files.

## Repository Scope And Sources Of Truth

- `pnpm-workspace.yaml` defines workspace membership; the root `package.json` defines the pnpm version and workspace commands. Paths below are repository-relative.
- The React renderer lives in `apps/desktop/src/`. The macOS shell in `apps/macos/` hosts it in a WKWebView: one SwiftPM package holds all shell logic, and a thin XcodeGen App target (`project.yml`; the generated `.xcodeproj` is not checked in) supplies the bundle. The native app is the only frontend; the renderer's client core (task cache, requests, provider client, and their schemas) lives in `apps/desktop/src/client/`. The Rust file index lives in the Cargo workspace under `crates/`, with the toolchain pinned by `rust-toolchain.toml`.
- Shared shadcn components and theme tokens belong to `packages/ui/`; shared TypeScript configuration belongs to `packages/typescript-config/`.
- The marketing website lives in `apps/website/` (`apps/website/README.md`): a Vite + React static site prerendered per language and deployed by the Vercel project `atd-agent` from `main`. It has its own fixed dark, monochrome design built on the apple-design web kit, not the renderer's shadcn preset, and it is not part of the native app.
- The launch film lives in `apps/promo-video/` (`apps/promo-video/README.md`): a Remotion project rendered on demand, never built or deployed with the rest. It recreates the product's interface in code, reads the shared brand assets in place, and scores its soundtrack in code from the same timeline as its picture.
- Treat source files, package scripts, and repository configuration as the source of truth for implemented behavior. Distinguish implementation evidence, agreed design decisions, and assumptions.
- For product design, Figma work, and analysis or review of behavior shown in a design, relevant project documentation is authorized task context. Search and read requirements, architecture plans, design sources, and their referenced artifacts in `docs/` and elsewhere in the repository as needed, without additional user confirmation. Keep reads scoped to the feature being designed or reviewed.
- Before defining interaction states, feedback timing, or plugin-specific UI, check the relevant documents for agreed capabilities, technology choices, plugin contracts, and lifecycle and failure behavior, then compare them with the implementation. Distinguish documented design decisions from implemented behavior; missing code does not mean an existing architectural choice is undecided. Follow current explicit user decisions over older documents and identify material conflicts instead of inventing behavior.
- Outside that design scope, do not use `docs/` as task context unless the user requests it. A user-requested plan and its referenced artifacts remain in scope for the task that created or approved them. Do not use private notes or Git stashes as task context unless the user requests them.
- Earlier content from the current conversation may be retrieved as needed, including after compaction. Other conversations and task histories require explicit user authorization, including listings with summaries, local logs, caches, and exports. Relevance alone does not authorize access.
- The upstream pi sources this project builds on are checked out locally, outside this repository, as read-only reference material: [earendil-works/pi](https://github.com/earendil-works/pi) at `${referenceRoot}/pi` (tag `v0.86.1`). The pins in `apps/agent-service/package.json` are `@earendil-works/pi-ai`, `@earendil-works/pi-coding-agent` and `@earendil-works/pi-mcp` at `1.0.0` (ahead of the checkout's tag, which predates `pi-mcp`). Consult the checkout to ground SDK and extension behavior; when its tag differs from a pin, the installed package under `apps/agent-service/node_modules/` is authoritative. Memory is the service's own engine (`apps/agent-service/src/memory/`); files adapted from pi-hermes-memory 0.9.9 keep their MIT attribution headers, with the license in `docs/third-party/pi-hermes-memory-LICENSE`.

## Task Execution

- Treat requests to implement, fix, or help perform an action as instructions to deliver the scoped result and applicable checks. Do not stop at a plan or an offer to continue. Respect requests limited to explanation, review, planning, or approval before implementation.
- Infer the intended outcome, acceptance criteria, and allowed side effects from the request and current conversation. Choose the simplest complete approach within the project constraints; use a plan when coordination or complexity warrants it.
- Resolve routine choices from repository evidence and conversation context. Ask for the smallest missing decision only when it materially affects correctness, scope, or consequential side effects and cannot be resolved from that evidence. Continue independent authorized work while waiting; a pending answer does not authorize dependent work.
- Carry authorization forward across follow-ups and compaction. Complete scoped, reversible work and permitted reads without repeated confirmation. When an action still needs approval, first finish the authorized preparation into a concrete, reviewable result. Do not add approval steps or warnings for hypothetical risks.
- Incorporate follow-up constraints without losing the original objective or completed work. Treat confirmed corrections as acceptance criteria for affected components and screens with the same purpose within the current scope; inspect their shared owner and consumers instead of waiting for repeated examples. Answer status or side questions, then resume unless the user cancels or changes the objective.
- Stop when the requested outcome is delivered, applicable checks are complete, and remaining limitations are reported. If blocked, finish independent work and state the exact missing decision, permission, or evidence; do not describe a partial result as complete. See [Validation](#validation) for the completion bar.

### Planning And Product Flows

- For formal requirements or architecture planning, resolve the shared models, ownership, data flows, lifecycle and failure behavior, and extension boundaries required by the agreed scope. Phased implementation must not defer these foundational decisions or omit agreed capabilities. Keep genuine unresolved decisions explicit and avoid speculative features outside that scope.
- Before expanding a product flow, map agreed capabilities to usable entry points, inputs and available options, primary actions, and relevant outcomes or error states. Keep this proportional to the task: a local visual correction does not require a new planning document or approval phase.

### Tools And Delegation

- Prefer scoped `rg` searches and direct reads of the relevant sources. Batch independent reads when useful; keep dependent actions and edits ordered. Broaden investigation when evidence is missing or contradictory, and stop once it supports the scoped decision.
- Use subagents only when explicitly requested by the user or applicable instructions. General model guidance about delegation does not authorize it. Assign bounded work, distinct file ownership, and acceptance criteria; do not overlap edits or disturb another active task. Keep messages readable and integrate the results before claiming completion.

## Commands And Local Runtime

- Before pnpm-based validation, confirm `pnpm --version` matches the root `packageManager`.
- `pnpm dev` starts the development agent service and the Vite renderer dev server, and on macOS builds the Debug app, mirrors it to `~/Applications/Atd Dev.app` (the copy it registers with LaunchServices and opens, because the widget extension cannot launch from under `~/Documents` and its widgets need an indexed location; the copy stays after `pnpm dev` ends), and opens it once both answer (`apps/macos/scripts/dev-open.mjs`, which passes `AI_AGENT_DATA_DIR` and `AI_RENDERER_DEV_ORIGIN` through, leaves an already-running Debug app alone, and quits the app it opened on exit). `pnpm dev:headless` starts only the service and the renderer. The service runs from source under `node --watch-path=src` and restarts within seconds when a service source file changes, interrupting runs in progress; the workspace packages it imports are built once at start and not watched. It uses the dev data dir `~/Library/Application Support/AgentService Dev`, and `AI_AGENT_DATA_DIR` overrides it. The default data dir `~/Library/Application Support/AgentService` belongs to the installed app; no development instance uses it. The product home (Personal skills and agents, product-skill records) follows the data dir: `~/.atd` only for the installed app's, `<dataDir>/atd` for any other, and `AI_ATD_HOME` overrides it (`resolveAtdHome` in `apps/agent-service/src/storage.ts`). `pnpm --filter @atd/agent-service seed:dev` seeds the dev data dir one way from the installed app's (settings, commands, provider connections with their credentials, Personal skills and agents) while `pnpm dev` is stopped; `--dry-run` lists what it would copy (`apps/agent-service/scripts/seed-dev-data.ts`).
- `pnpm dev:renderer` runs only the renderer dev server. The page runs only inside the macOS shell: a plain browser on the dev server gets no `window.desktop` bridge and shows only a notice (`common:hostRequired`), and the service hosts no web page. `pnpm --filter @atd/desktop build` builds the renderer (`dist-native`) that the Release app embeds. Inspect `apps/desktop/vite.config.ts` for the configured host and port (5173 unless `AI_RENDERER_PORT` moves it; the Debug app then needs the same origin in `AI_RENDERER_DEV_ORIGIN`); do not invent a different origin.
- `pnpm --filter @atd/macos build` generates the Xcode project with XcodeGen and builds the arm64 Debug app into `apps/macos/DerivedData/Build/Products/Debug/Atd.app`; the Swift checks need macOS 26 with Xcode 26, XcodeGen, and SwiftLint. The Debug app (bundle id `com.junerdd.ai.dev`) never launches, replaces, or stops a service: before each connection it rereads `endpoint.json` and the token in the dev data dir (or in `AI_AGENT_DATA_DIR`), connects to the service `pnpm dev` runs, and shows a "run pnpm dev" state when none answers. Release builds (`com.junerdd.ai`) start their bundled service themselves. Builds are ad hoc signed unless `AI_CODE_SIGN_IDENTITY` names a code signing identity (such as `Apple Development`, with its team in `AI_DEVELOPMENT_TEAM`); macOS ties Screen Recording and Accessibility grants to an ad hoc build's cdhash, so every rebuild drops them, while builds signed by one certificate keep them. `StaleGrantRecovery` resets and asks again for grants a new signature left stale.
- `pnpm build` builds every workspace package: the renderer, the service and shared packages, and the Debug native app. `pnpm --filter @atd/macos build:release` builds the Release app into `apps/macos/DerivedData/Build/Products/Release/Atd.app`: its `bundle` step builds the service and the renderer and stages the service pack with the pinned Node.js (`apps/macos/scripts/prepare-service-pack.mjs`), which the Release-only phase in `project.yml` embeds. Inspect those scripts and `project.yml` before changing packaging behavior.
- Releases come from `.github/workflows/release.yml`: raising `version` in `apps/macos/package.json` on `main` (equal to `MARKETING_VERSION` in `project.yml`) builds the Release app on `macos-26` and publishes `v<version>` with an arm64 dmg, whose installer window `apps/macos/dmg/package.mjs` lays out with hash-pinned dmgbuild; a manual run releases the current version when its tag is absent. The app is signed with the self-signed release certificate (the `RELEASE_SIGNING_P12` secrets, pinned by `RELEASE_SIGNING_SHA1`, whose public half is `apps/macos/release-certificate.pem` and whose private key is kept outside the repository; replacing it drops every installed copy's privacy grants once) and not notarized. Release builds update themselves with Sparkle (`AppUpdater`) from the `appcast.xml` each release publishes and the download mirror (`ops/release-downloads/`) republishes on R2 against its verified dmg, signed with the `SPARKLE_ED_PRIVATE_KEY` secret that matches `SUPublicEDKey` in `project.yml`; Debug builds never update. Bump `apps/desktop/package.json` with it.
- `pnpm test` runs Vitest, the service's Node tests, and Swift Testing in `apps/macos`; `pnpm --filter @atd/desktop test:watch` watches existing tests.
- Start runtime work — the service or the native app — when a task's acceptance criteria depend on rendered or native behavior, and prefer the smallest launch that answers the question: the service alone for HTTP and stream behavior; the Debug app for layout, styling, copy, bridge, window, and native-surface behavior. Do not launch for unrelated tasks.
- Run every instance you start with its own temporary data directory and on a port you verified is free, so it cannot disturb a session the user is running. Never stop, restart, or attach automation to an app, service, or development server owned by the user or another task; an already-running instance does not authorize inspection.

A task-started service, Debug app, or Release app gets a temporary `AI_AGENT_DATA_DIR`, and a Debug app launched with the same value connects only to that task's service. A debug session can read and change everything the app can see: never point it at the user's data directories, and attach to a session the user is running only when the user asks for that inspection.
- A Release build shares the bundle id `com.junerdd.ai` with the installed app (the Electron 0.2.1 release until the P7 switch), and with it the Accessibility grant and the single-instance check. Run it only briefly with the installed app quit, and expect to grant the installed app Accessibility again afterwards.
- Debug builds set WKWebView [`isInspectable`](https://developer.apple.com/documentation/webkit/wkwebview/isinspectable). The expected path is Safari → Settings → Advanced → "Show features for web developers", then Develop → this Mac → the Atd page. WKWebView exposes no CDP endpoint, so CDP clients such as chrome-devtools-mcp cannot attach to the native app.
- Launch on a port you verified is free (`lsof -nP -iTCP:<port> -sTCP:LISTEN`), poll it for readiness instead of sleeping, and stop only the instances you started. The `pnpm dev` service takes an OS-assigned port; the Vite port is fixed (5173 unless `AI_RENDERER_PORT` moves it, and `scripts/dev-guard.mjs` refuses a busy one), so verify it is free first. A fresh data directory starts with no stored language, so the page resolves it from the OS locale.
- Renderer probes that POST to a loopback collector are blocked by the CSP header the scheme handler sends (`apps/macos/Sources/AICore/Relay/ContentSecurityPolicy.swift`; `index.html` has no meta CSP) — a passing `curl` never proves the page's fetch works. Temporarily extend the development `connect-src` with the collector origin, rebuild and reopen the Debug app (HMR does not refresh a CSP), and revert the edit at cleanup without committing it.
- The renderer is a WebKit page; the Swift shell is not a page. Use Xcode's debugger or the app's logs for the shell, the relay, and window geometry.
- Keep throwaway debugging scripts and screenshots in gitignored `tmp/` or `apps/desktop/.artifacts/`, and extend the existing Vitest, service, or Swift tests for durable checks instead of adding a parallel harness.

## Code Conventions

- Use TypeScript and functional React for the renderer and the service, Swift 6 with complete strict concurrency checking for the macOS shell, and Rust for the file index. Follow `.oxfmtrc.json`, `.oxlintrc.json`, `apps/macos/.swift-format`, rustfmt, Clippy, and the conventions of the nearest feature.
- Every maintained `.ts`, `.tsx`, `.swift`, and `.rs` file must have at most **350 lines**, including blank lines and comments. This includes declaration files, tests, configuration files, `Package.swift`, and checked-in shadcn components. Each language has an enforcing error: the `max-lines` override in `.oxlintrc.json` for TypeScript, SwiftLint's `file_length` rule (`apps/macos/.swiftlint.yml`, the only rule it runs) for Swift, and `scripts/check-rust-file-length.mjs` (part of `pnpm check:rust`) for Rust, which has no built-in file-length lint. Generated build output remains excluded by the existing ignore patterns.
- Keep the limit after formatting. Do not compress code, remove useful comments, suppress `max-lines` or `file_length`, or add file exclusions merely to pass the limit. Split responsibilities at meaningful boundaries before a file grows beyond it.
- Prefer behavior-preserving simplifications that remove avoidable branches, modes, layers, duplicated ownership, and special cases. Use the simplest implementation that satisfies the requirement.
- Comments should explain non-obvious intent, contracts, ownership, ordering, or failure behavior. Skip comments that restate the code; use JSDoc for exported contracts when names and types do not explain their semantics.
- Fix the owning contract or data flow when addressing a bug. If only a mitigation is safe, identify it and explain the remaining root cause.
- Validate uncertain data at runtime boundaries and express internal invariants in types. Do not use `any`, broad casts, optionality, speculative fallbacks, or retries to hide an unresolved contract.
- Keep behavior with the module that owns the concept. Decomposition should leave the original module with less responsibility and give the new module a clear purpose with narrow, one-way dependencies. Avoid pass-through modules and generic helper collections created only to reduce line counts.
- Components should handle rendering, composition, and local event wiring; hooks should orchestrate React state and effects. Place independent domain logic in the nearest feature-owned helper when separation improves clarity. Do not extract trivial logic solely to satisfy a directory rule.

## Internationalization

- The renderer ships `en` (source language) and `zh-CN` through i18next + react-i18next, initialized once in `apps/desktop/src/i18n/index.ts` and imported by the renderer entry and the test setup. Components use `useTranslation('<namespace>')` with relative `t('group.key')` calls; keys are typed from the English JSON, so pass literal key strings and let type checking catch typos.
- Translations live in `apps/desktop/src/i18n/locales/<lng>/<namespace>.json`, one namespace per feature area (`settings`, `providers`, `commands`, `memory`, `panel`, `tasks`) plus `common` for copy shared across features such as the global toast dismiss control. Register a new namespace in `apps/desktop/src/i18n/index.ts`. English and Chinese files keep identical key sets; English is the source of truth, and existing tests assert some English values, so do not reword an English value while migrating it.
- Migrate copy incrementally: when a change touches a component that still renders user-facing literals, move that component's copy into the locale files in both languages as part of the change. Write real product translations instead of placeholder or machine-looking text; keep interpolation placeholders, ellipses, spacing, and the intent of aria-labels and tooltips.
- The language preference is persisted by the service (`language` in `/v1/settings`, validated against `APP_LANGUAGES` from `@atd/agent-contracts`, which the renderer re-exports as `LANGUAGE_CODES`) and resolves from the OS locale while none is stored. The settings-window header selector changes it; both renderer windows apply it through `useAppLanguage`, so the panel follows without a reload, and the native host pushes it to the shell (`language.set`). To add a language, extend `APP_LANGUAGES` and `resolveLanguage`, add its locale folder and resources, and add its endonym to the renderer language names.
- Do not translate provider names, model IDs, agent output, logs, or other runtime data. The native Swift surfaces (menu bar menu and tooltips, alerts, window titles, connection states) take their copy from a String Catalog in `apps/macos` with `en` and `zh-Hans`, and follow the service language setting the renderer pushes, using the system language until the first push; add every new shell string to the catalog in both languages. Provider catalog metadata and service validation messages remain English-only. Because a locale can legitimately cover part of the UI, report remaining gaps instead of claiming full localization.
- Keep locale JSON formatted with `oxfmt` and type-check after adding or renaming keys; a missing key falls back to English rather than the raw key. Runtime and native verification of the selector still follows [Commands And Local Runtime](#commands-and-local-runtime) and [Visual Acceptance](#visual-acceptance).

## Community Reuse Before Custom Implementation

Deliver the requested behavior with less custom infrastructure to maintain.

- Before implementing or delegating a reusable capability such as shortcut recording, key matching, forms, or accessible controls, inspect the relevant feature, shared packages, platform APIs, and installed dependencies, then research suitable community libraries. Prefer suitable reuse over custom infrastructure. Verify dependencies in this repository; absence from the project alone does not make a library unsuitable.
- Use current official documentation and upstream source or releases to check the closest candidates against required behavior, framework and runtime compatibility, release maturity, maintenance, license compatibility with the repository's MIT `LICENSE`, and dependency cost. Stop when there is enough evidence to choose a solution or establish a concrete gap, before committing to custom implementation. Trivial business logic and straightforward glue code do not require a separate library or extended research.
- Reuse the chosen library's supported APIs and compose existing components. Keep custom code limited to uncovered business rules and necessary integration, such as the native bridge, persistence, or native accelerator conversion. Do not duplicate a library's event handling, parsing, recording, or state management behind a new wrapper. Product controls should continue to reuse shadcn components from `packages/ui`.
- When proposing custom reusable behavior, name the existing or community solutions checked, link the evidence, and identify the unmet requirement or disproportionate integration cost. Familiarity, imagined flexibility, a failed search, or already-written custom code is not sufficient justification.
- When delegation is authorized, include the accepted reuse decision and evidence in worker contracts before dispatching dependent implementation. Resolve an uncertain library choice through focused research first. If new evidence changes that choice, coordinate the affected work and remove superseded duplication during integration while preserving unrelated changes.
- Selecting and integrating a suitable dependency is part of authorized implementation, subject to explicit user constraints and repository dependency rules. Verify the integration through [Validation](#validation) and report the reuse decision and remaining custom boundary. This does not authorize unrelated migrations, dependency upgrades, new tests, or unrelated runtime launches.

## Native Shell And Design Boundaries

- Keep native capabilities in the Swift shell. The page reaches them only through the typed native bridge (`apps/desktop/src/native-bridge/contract.ts` is the source of truth; the Swift Codable types are generated from its exported JSON Schema) and reaches the service only through the relay. The page never holds the service token: the scheme handler forwards allow-listed `/v1` routes and sets `Authorization` itself. Do not add a side channel that bypasses either.
- Accept script messages only from the main frame of the `ai-app://renderer` origin and validate every payload at the shell boundary. Preserve the navigation lock (no subframe navigation; the main frame stays within `ai-app://renderer`), the CSP headers, and the relay's path normalization, default-deny route matching, and origin and `x-ai-relay` checks.
- Position windows using display work areas in logical points; handle negative monitor coordinates and small displays. The page reports its drag regions to the shell, which starts native window drags; WKWebView ignores `-webkit-app-region`.
- Review the window, its `NSGlassEffectView`, the WKWebView configuration, and the renderer root styles together when changing corners, transparency, borders, or shadows. `NSGlassEffectView` is the background of the panel and the settings window and owns the outer clipping, edge, shadow, and desktop backdrop; do not duplicate these effects with a CSS window shell. The WKWebView above it is transparent only through the private `drawsBackground` key-value setting, which has no public replacement; keep that dependency in one place.
- Keep `html`, `body`, and `#root` transparent and fill the web view edge to edge. The panel may paint a shared, token-based translucent or opaque content surface when required for readability or the approved design. The native glass supplies desktop blur; the renderer controls the content surface color and opacity. Give that fill one owner, avoiding duplicate tint layers in the window, the web view, root elements, or pseudo-elements. Remove competing outer CSS radii, borders, and shadows; do not use a fill to conceal incorrect clipping or corner seams.
- In-page glass (overlays such as menus, selects, popovers, dialogs and sheets; the task panel's glass controls through `Button` `variant="glass"`/`"glass-ghost"` and `glass-control`/`glass-state`; the buttons of floating `overlay-footer` action bars, except a solid primary commit action such as Save; the settings navigation drawer) uses the single glass material, the `surface-glass` utility in `packages/ui/src/styles.css`; consumers tune its tokens (`--ata-glass-fill`, `--ata-glass-blur`, `--ata-glass-shadow`, `--ata-glass-material`) instead of setting their own fill, blur, or shadow. WebKit fills a glass element's whole composited layer, which grows with every outset box-shadow, ring, or outline on it, so a glass element never carries outset effects in any state: states and focus rings draw inside its border box, and glass never stacks on glass. In the shell it renders WebKit's system glass (`-apple-visual-effect: -apple-system-glass-material`), which the web view enables through the private `useSystemAppearance` preference (`apps/macos/Sources/AIShell/Web/WebKitPrivate.swift`); the utility's `backdrop-filter` fallback renders in any WebKit that drops the preference. The fallback blurs page content, never the desktop. The utility also owns the inactive-window and reduced-transparency states (WebKit has no `prefers-reduced-transparency`, so the shell reports the system setting through the `accessibility.reduceTransparency` bridge event as `data-reduced-transparency` on the root element; styles key off that attribute, not the media query alone), and sets `--accent` and `--muted` to the glass wash, so item highlights and muted fills on glass stay translucent; a surface inside glass uses those tokens rather than an opaque color of its own. Controls that were transparent and borderless before they became glass (the task panel's header buttons and the pills under the composer) use `variant="glass-ghost"`: no fill, edge or shadow at rest, only the glass washes and inner focus ring; controls that had a border or a fill of their own (the composer field, the progress capsule, scroll-to-bottom, overlay footer buttons) keep real system glass, whose rim no token removes.
- Do not copy a Figma radius onto an already rounded native window. Map design effects to their owning layer instead of rendering them twice.
- Reuse `packages/ui` components and design tokens. For Figma work, inspect variables, styles, effects, and existing mappings before introducing literal values or duplicate components.
- By default, synchronize user-requested visual and interaction changes between the canonical project Figma file and application code in the same task. Update shared components, states, tokens, and affected review examples together; verify the previous agreed design values are preserved. The user does not need to repeat this requirement. Respect explicit design-only, code-only, research, or approval-before-implementation requests. If either side cannot be updated, report the unsynchronized scope and reason instead of claiming both are complete.
- Discover cloud Figma tools first. Use the local Figma connection only when cloud access or a required capability is unavailable, or when the user requests local access; verify the target file and node before using a local selection.
- Preserve exact exported design assets in the repository rather than relying on expiring URLs. Represent implemented behavior honestly; do not present local task storage as a connected AI service.

## shadcn Preset Fidelity

- The approved preset is `b27GcrRo`: Radix / Rhea, Neutral base and theme, Inter with inherited heading font, Lucide, default radius, subtle menu accent, and default menu color. The canonical initialization command is exactly `pnpm dlx shadcn@latest init --preset b27GcrRo --template vite --monorepo --pointer`; it defines this project's Vite monorepo setup and does not authorize rerunning initialization or upgrading an existing project.
- Use the [official preset examples](https://ui.shadcn.com/create?preset=b27GcrRo&pointer=true) for visual comparison. The command above is the source of truth for project initialization; preserve the project's Radix base and pointer preference when comparing examples.
- The [official Rhea style](https://ui.shadcn.com/docs/changelog/2026-05-rhea) combines rounded geometry with compact controls, tighter spacing, and greater information density. Preserve that combination in lists, forms, menus, and dialogs. Use the component size variants to achieve density; do not change the global spacing scale or introduce oversized rows and empty gaps as a substitute for hierarchy.
- Before designing or implementing controls, inspect both `components.json` files, `packages/ui/src/styles.css`, and the relevant checked-in component variants. Use the installed CLI's read-only preset decoding when needed. Match the resolved preset and actual component defaults, not a generic notion of shadcn or a skill's suggested default style.
- Select the primitive by its interaction: ordinary `Item` content, menu or command options, `Select`, `Dialog`, `Popover`, and `Tooltip` retain their own geometry and state contracts. Match the user's described behavior to the actual variant; a shared label such as "default" does not make variants equivalent. Do not apply ordinary Item or Button geometry to menu options solely because they contain text and an action.
- Figma components must match the selected Rhea variants in geometry, control height, padding, gaps, typography, fill, border, and supported states. A connected Nova, Vega, or other-style library instance does not by itself satisfy the Rhea requirement; matching only the font and color is insufficient.
- Reuse existing project Rhea components, variables, and text styles first.
